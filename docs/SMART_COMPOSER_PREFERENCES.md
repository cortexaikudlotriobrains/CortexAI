# Smart composer preferences

Ask's **More options** menu starts with **Smart in new chats** and **When Smart is off**. Its header omits the redundant **Smart Ask** and **Manual Ask** status labels on desktop and mobile. Compare retains its mode caption and shows only **When Smart is off**, because Compare always submits explicit targets. Improve prompt and Reasoning remain message controls.

`smartForNewChats` starts as `true`; `smartOffModelId` starts as `null`. The repository has a legacy read-only database preferences helper, but no user-preferences HTTP API. React therefore stores these preferences at `localStorage["cortex.composerPrefs.v1"]`, with a separate entry for each authenticated `whoAmI.user_id` and an anonymous entry. Changes sync between tabs on the same browser through the storage event. This fallback does not sync between devices. Invalid or inaccessible storage uses the initial values; storage failures do not prevent editing in the current tab. The former flat prototype shape is read only for anonymous users.

`store/composerPrefsStore.ts` owns storage and `resolveSmartOffModel`. The resolver accepts the current catalogue and locked keys derived from server entitlements. Unset, disabled, unselectable, missing, or locked saved IDs resolve to the eligible plan model in `config/askDefaults.ts`: Free uses `openai:gpt-5.6-luna`, Plus uses `claude:claude-sonnet-4-6`, and Pro uses `openai:gpt-5.6-terra`. If that plan model is absent, use an eligible catalogue model. Keep the saved ID so an upgrade or catalogue restoration can make it usable again. Browser preferences never authorize model access; the backend still enforces entitlements.

New Ask chats read the saved Smart switch preference once. The composer Smart button and Smart in new chats switch in More options both display the current Ask chat state and use the same toggle handler. Toggling either saves that preference and immediately updates Smart in the current Ask chat, including an existing session with a transcript. The row keeps the fixed subtitle New chats start with Smart on in either switch state; the model name appears in When Smart is off. Turning Smart off selects the chat's last manually picked model, or the resolved Smart-off model if none has been picked, and resets reasoning to that model's lowest supported level. Turning Smart on uses Auto reasoning and retains the last manual choice. The model picker remains chat-scoped and does not change preferences. Reopened chats keep their own Smart state, and the menu displays that state even if the saved preference for new chats differs. Changing the saved Smart-off model or receiving a preference update from another tab does not rewrite the current Ask state. New chat resets chat selections and reasoning, preserves the current workspace mode, and reads preferences again.

Chat Smart state, last manual model, selected model, Compare slots, and whether Compare has sent are stored separately at `cortex.chatComposer.v1`, keyed by user and backend session ID. Reopening history restores that session's state; on another device with no snapshot, routing metadata and the latest persisted Ask/Compare responses supply the state. Legacy Ask history without routing metadata retains Smart mode. Reload waits for history before initializing or writing session choices, and Compare uses canonical requested IDs when the provider's served ID differs. Preferences never rewrite history. These local snapshots contain model IDs and routing state, not prompt or response content.

New Compare sessions start with the resolved Smart-off model in slot 1 and `claude:claude-sonnet-5` in slot 2. If slot 1 is Sonnet 5, slot 2 prefers `openai:gpt-5.6-luna`. Fill missing or locked initial alternatives with distinct plan-eligible models. Slot 1 follows resolved preference changes until the first accepted Compare send, including optimization before streaming; automatic slot changes stop after that send even if generation fails or the catalogue changes. Manual Compare selections still work. Add/remove controls retain the two-target minimum and current plan limits.

Desktop uses a 400px popover anchored to the sliders trigger, opening above it when space permits. The provider and model lists replace content inside the same menu. Manual Ask offers **In use now** when its model differs from the resolved preference. Selecting an unlocked model saves immediately and returns to the main view with **Saved** for 1800ms. Selecting a locked model opens the existing upgrade dialog and keeps the model list available underneath it.

At widths of 760px or less, More options uses a modal bottom sheet with **Smart** and **This message** cards, Done, a backdrop, and a drag-to-dismiss grabber. Reasoning becomes **Auto · Low · Med · High · Max**, with full accessible names and one description for the selected level. Unsupported levels remain disabled. The footer always ends with **Higher reasoning may take longer and use more AI credits.** Desktop retains the five descriptive reasoning rows.

Escape steps models → providers → main → closed. Navigation focuses the back button; going back focuses the row that opened the level. Closing resets the view and restores trigger focus. Switches expose `role="switch"`, provider/model lists use `listbox`/`option`, and Reasoning uses `radiogroup`/`radio` with arrow-key selection. The mobile sheet traps Tab and locks background scrolling while active; its keyboard handling yields to the upgrade dialog. Entry, switch, and save animations honor reduced motion. All surfaces use the existing light/dark theme tokens. The composer body rises above the model row while options are open.

Validation lives in `ComposerOptionsMenu.test.tsx`, `composerPreferences.test.tsx`, the updated composer/default tests, and `e2e/responsive/fixtures/smart-preferences.mjs`, exercised by both mobile and desktop/iPad suites. The browser scenarios cover next-chat initialization, preference isolation, Compare freezing/collision, plan locks, menu layers, navigation focus, mobile segments, theme, and reduced motion.

No API request/response schema, Postman request, database migration, provider routing policy, or operational deployment switch changes with this frontend feature. The existing model-options, entitlements, history, Ask, and Compare endpoints retain their contracts.
